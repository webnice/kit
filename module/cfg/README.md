# module/cfg

`module/cfg` — базовое ядро приложений, построенных на `github.com/webnice/kit/v5`. Пакет выполняет роль дирижёра запуска: собирает bootstrap-конфигурацию, разбирает CLI и переменные окружения, регистрирует компоненты, проверяет их зависимости и конфликты, упорядочивает запуск, управляет уровнями работы приложения (`runlevel`) и аккумулирует ошибки.

Пакет является singleton-объектом: после импорта конфигурация создаётся в `init()` и далее доступна через `cfg.Get()`.

## Состав пакета

| Путь | Назначение |
|---|---|
| `module/cfg` | Публичное ядро конфигурации: `Interface`, `Essence`, регистрация компонентов, runlevel, пути, ошибки. |
| `module/cfg/cli` | Командный интерфейс приложения. |
| `module/cfg/const` | Константы имён специальных переменных окружения и внутренние константы `cfg`. |
| `module/cfg/cpy` | Копирование конфигурационных структур с фильтрацией полей. |
| `module/cfg/reg` | Точка регистрации компонентов приложения. |

## Основные сущности

- `cfg.Interface` — основной интерфейс конфигурации: доступ к логированию, CLI, версии, UUID, серверу, путям, конфигурационным объектам и ошибкам.
- `cfg.Essence` — служебный интерфейс (`Gist()`), через который выполняется большинство операций запуска: регистрация, runlevel, компоненты, конфигурация.
- `cfg.Recorder`/`cfg.Version` — внутренние интерфейсы записи/версии.
- `kitTypes.Component` — контракт пользовательского компонента (`Preferences`, `Initiate`, `Do`, `Finalize`).
- `RunlevelSubscriberFn` — функция подписки на изменение уровня работы приложения.

## Жизненный цикл приложения

Дирижёр жизненного цикла находится в `app.Main()`. `module/cfg` предоставляет ему состояние, регистрацию и функции перехода между уровнями.

Ключевые уровни:

| Runlevel | Действие |
|---:|---|
| 0 | Старт приложения, импорт пакетов, регистрация компонентов и конфигурационных объектов. |
| 1 | Инициализация менеджера логирования. |
| 2 | Опрос компонентов: сбор `Preferences`, формирование очерёдности. |
| 3 | Проверка конфликтов компонентов (`conflict`). |
| 4 | Проверка обязательных зависимостей (`requires`). |
| 5 | Сортировка компонентов по правилам `before` и `after`. |
| 6 | Инициализация CLI и переменных окружения. |
| 7 | Построение карты дальнейших runlevel. |
| 8 | Вызов `Initiate()` у компонентов. |
| 9 | Подписка внутренних обработчиков на изменение runlevel. |
| 10..Targetlevel | Последовательный запуск `Do()` компонентов. |
| 65535 | Завершение: `Finalize()` компонентов, остановка bus/logger, вывод накопленных ошибок. |

`Targetlevel` определяет, до какого уровня дирижёр сам переключает приложение. Если компонент на своём `Do()` вернул `done=true`, дальнейшее управление runlevel передаётся компонентам.

## Регистрация компонентов

Компоненты регистрируются через `module/cfg/reg`:

```go
func init() { reg.Registration(&MyComponent{}) }
```

Регистрация возможна только на runlevel 0. `reg.Registration` вычисляет имя компонента как `PkgPath` типа, проверяет повторную регистрацию и сохраняет объект во временном списке. После закрытия регистрации `app.Main()` переносит объекты в основной список через `ComponentPreferences`.

Пользовательский компонент реализует `kitTypes.Component`:

```go
type Component interface {
    Preferences() ComponentPreferences
    Initiate() error
    Do() (done bool, levelExit bool, err error)
    Finalize() error
}
```

Правила запуска описываются `ComponentPreferences`: `Before`, `After`, `Require`, `Conflict`, `Runlevel`, `InitiateTimeout`, `IsDisable`.

## Потокобезопасность и важные инварианты

- Компонентные callback-функции (`Preferences`, `Conflict`, `Requires`, `Sort`, `Initiate`, `Do`, `Finalize`) не вызываются с удержанием `ComponentMutex`. Список компонентов копируется под блокировкой, после чего пользовательский код выполняется вне её. Это защищает от self-deadlock, если компонент обратится к `ComponentNames()` или другим gist-методам.
- `ComponentSort` сортирует снапшот указателей и фиксирует новый порядок только после успешного завершения callback-функции.
- `mapRunLevel` защищён отдельным `runLevelMutex` и публикуется атомарно.
- Подписки на runlevel хранятся в `container/list`, но все операции со списком выполняются под отдельным `runLevelSubscribersMutex`; перед диспетчеризацией подписчики копируются в срез.
- `Runlevel()` может только увеличиваться. Попытка установить меньший уровень добавляет ошибку `RunlevelCantLessCurrentLevel`.
- Ошибки приложения аккумулируются в списке `error`; `ErrorAppend`/`IsError` защищены `errorMutex`. Другие участки кода, добавляющие ошибки на ранних этапах инициализации, выполняются до старта конкурентного runlevel-цикла.

## Конфигурация

Bootstrap-конфигурация формируется из значений по умолчанию, CLI и переменных окружения. Основные поля:

- директории: home, working, temp, cache, config, log;
- файлы: config, pid, state, socket;
- `ApplicationTargetlevel`, `ApplicationDebug`, `ApplicationName`, `LogLevel`;
- режим fork worker.

Дополнительные сегменты конфигурации регистрируются через `Essence.ConfigurationRegistration`. Для сегментов поддерживаются callback-и изменения, YAML-теги и значения по умолчанию.

## CLI

CLI инкапсулирован в `module/cfg/cli`. Публичный API регистрации команд и флагов сохранён:

```go
cli.RegisterCommand(&cli.Command{Command: "serve", Description: "...", Value: &cmdValue})
cli.RegisterFlag(&cli.Flag{Flag: "config", ShortKey: 'c', Environment: "APP_CONFIG", Value: &configPath})
```

Внутренняя машина парсинга находится в `cli`. Типы и функции имеют имена `NewKong`, `Kong`, `KongCommand`, `KongFlag`, `KongErrors`, `ReprString`, `ReprPrinter` и т.п.

## Ошибки

Все ошибки пакета описаны в `cfg.Errors()` и суб-справочниках (`cli.Errors()`, `cpy.Errors()` и др.). Ошибки из пользовательских callback-ов разбираются через `Errors().Unbind`, чтобы извлечь код ошибки `uint8`. При завершении приложения печатаются все накопленные ошибки, а код возврата выбирается как максимальный код ошибки.

## Тестирование

Для пакета добавлены регрессионные тесты:

- `RegistrationMain` не оставляет `FnMutex` заблокированным при panic;
- `ComponentInitiate` не self-deadlock’ится при обращении к `ComponentNames()`;
- `ComponentPreferences`, `ComponentCheckConflict`, `ComponentRequiresCheck`, `ComponentSort` не держат mutex во время пользовательских callback-ов;
- конкурентная подписка/отписка/диспетчеризация runlevel не паникует;
- `ErrorAppend`/`IsError` безопасны при конкурентном использовании;
- базовый API `module/cfg/cli` и перенесённые тесты `repr`.

Проверки: `go test -race ./module/cfg/...` и `go vet ./module/cfg/...` должны проходить.
